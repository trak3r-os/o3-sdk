# o3-sdk and o3-303 against Polyend's tracker-ce

A comparison made on 2026-11-03 of o3-sdk and o3-303 with Polyend's published firmware source, github.com/polyend/tracker-ce. Nothing
from it is copied into either repository: this file holds leads to verify against the NXP reference manual, the datasheets or the unit,
never against tracker-ce's code. The maintainer asked for it to be kept in the repository (2026-11-03). Paths without a repository
name are o3-sdk's.

## Summary

github.com/polyend/tracker-ce is the official firmware source (PolyForm Noncommercial 1.0.0 + Polyend permissions; synth/lib/*.a proprietary). It is GPL-incompatible and the CLAUDE.md hard rule bans code/assets/RE material from it. Nothing is copied. Four read-only subagents compared it with o3-sdk and o3-303 on 2026-11-03 (clean-room style: facts only, no code, no tables). Their `3rdparty/` (Teensy/NXP: SAI, SGTL5000 init, eDMA, USB core) was not read by the four agents; a later reference read covers it (below). The NXP/SGTL5000 datasheets and upstream PJRC (MIT) have the last word.

## Open decision for the maintainer (provenance, hard rule)
- `o3-sdk/kit/core/include/o3sdk/core/scales.h`: names, order, trailing space in "Phrygian ", and the duplicated Dim/WholeHalf mask match CE's table (lists compared by eye by one agent). Header says it is track3r-os interoperability data (OS-009, PAR-073) and calls its match with the official firmware "an open research question". Decide: keep with a note, or rebuild names/order from scratch.
- `kit/app/.../brightness.h`: display duty steps 20/50/128 and pad-light scaling by thirds also match CE. Header cites track3r-os OS-CFGWIRE. Confirm that is where they came from.

## Measure on the unit (ranked)
1. Backlight PWM: we never write REG_PWM_HZ (chip default 250 Hz), duties 20/50 may flicker or couple a 250 Hz tone into audio; CE writes ~9 kHz on the full-size unit (the board's backlight driver may differ). Slow-motion video, scope, line-out spectrum. Our code: platform/mk66/display/src/chip.cpp, device.cpp bring_up, InitConfig::backlight_hz=0.
2. USB MIDI on Windows 11 (March 2026 update or later), modes STANDARD/AUDIO/DISK, plus macOS. CE's changelog lists a fix for it. Ours measured on Linux only. Also check the MIDI-streaming class header total-length convention (header+jacks only in ours, kit/usb/src/descriptors.cpp:81-97; the USB MIDI 1.0 appendix may include the endpoints). Read USB MIDI 1.0 6.1.2.1 and Appendix B first; change nothing until a host test says so.
3. Sample rate: CE runs 180 MHz x 16/255/256 = 44117.647 Hz; ours exactly 44100 (196/3125); the 4080/1 build option reproduces CE's. Frequency-count LRCLK, A/B noise floor and spurs; this also settles SCLKFREQ 32 Fs vs 64 Fs (sgtl5000.h open A/B, HW-A E-1).
4. PTE26 line-in switch polarity: CE agrees with our assumption (high = jack and mic, low = radio). One measurement turns "assumed" into "confirmed" in board.h. Boot position differs (CE parks on the jack, ours on the radio).
5. Power-off current and wake (our QA-GLB-103/117, power_off.h:36-47); force a reset from the low-power state and check it returns to HSRUN 180 MHz with SDRAM up (BLPE in ours, crash_store.cpp:101).
6. USB interrupt priority (ours 64, below the audio DMA ISR, above render at 128; CE has USB highest): worst-case USB ISR in AUDIO and DISK modes against the 60% render budget.
7. USB MIDI host burst/flood test, MIDI clock-out jitter and start alignment over hours, DIN loopback (31.25 kbaud, idle-high TX at hand-over). CE needed fixes for drops, drift and a start one clock late.
8. 100 cold boots with an SDRAM pattern test; 3 different SD cards x 20 cold boots, pull-card-mid-write; CE waits 500 ms after SD power-up, check ours (sd_policy.h, card_swap.cpp).
9. Button TCA8418: ours scans 8x10 (C9 included), CE 8x9. Check the schematic for what C9 is wired to. Pad chip is 8x10 in both.
10. I2C0 (buttons + codec) has no glitch filter in ours (filter 4 only on I2C2; CE uses 4 on both). Check InputStats::errors and SCL/SDA on a scope with USB+SD+audio active. Touching it affects audio bring-up.
10b. FT812 touch engine (raised after the second read: CE sets REG_TOUCH_RZTHRESH 1200 against false touches): read REG_TOUCH_RZ / RAW_XY / TAG for a minute on the unit; if they report touches, write REG_TOUCH_MODE = 0. Cheap.
11. 16-bit FT812 reads: CE adds ~3 us around CS, ours has none (chip.cpp:139,150,185,308). 1e5 rd16 at 18 MHz, count mismatches, with audio running.
12. Build: kit DSP at -Os (MinSizeRel, gcc 15.3) vs CE's -O2: measure CPU; re-run nm for __aeabi_d*; check 32-bit DWT wrap (23.9 s at 180 MHz) in every profiling site.
13. Lower: IS31FL3731 health check reads back only the shutdown register every 500 ms (CE reads back ~12 function registers per frame, pad_leds.cpp:198-232); DMA failure classification uses the global DMA_ES valid bit and can latch display DMA to polled for good (device.cpp:312, display.cpp:94-100); FT812 touch engine at defaults (read REG_TOUCH_* once); soft-off leaves DISP high and PCLK running (power_host_mk66.cpp:273-286); mic/line source switch has no soft-mute (CE mutes 200 ms); CHIP_ANA_POWER after stop 0x4060 vs CE 0 (current draw); USB bMaxPower 100 mA placeholder; SYSMPU grants only master 4 (USB), a future SDHC ADMA needs master 5; PTE28 (Si4703 GPIO2) not named in board.h; encoder acceleration is app policy in ours, platform-level in CE.

## Risks in our code, confirmed by reading it (changes would go to o3-sdk)
- No NaN/Inf guard in `Engine::render` (kit/dsp/src/engine.cpp:28-36,770-831): a poisoned filter/delay state silences that voice until power cycle (the MK66 output kernel maps NaN to 0, so the speaker is safe). Plan: host fuzz of every unit with extreme parameters + finite-output assertion, then a per-slot guard.
- No FZ (flush-to-zero) set anywhere; only acid_voice flushes denormals; units/delay and the engine do not. Cost on the M4F unmeasured: `cycles_max` with a long silent delay tail at max feedback.
- No master limiter or compressor (stacked drive + delay + accent only coloured). A float limiter unit as a master insert needs no kit change.

## Ideas only CE has (design independently from literature, never from CE)
- SGTL5000 DAP (powered, unused): free master EQ/AVC limiter, maybe a mic leveller for the vocoder; confirm ADC-to-DAP routing in the datasheet, measure latency.
- Reverb: port Mutable Instruments' from upstream (MIT, with attribution), answers DESIGN-303 "Reverb send".
- Vocoder helpers: mic noise gate (hysteresis, hold), offline SOLA/WSOLA loop stretch for TUNE, count-in + monitor-only bus for loop recording, chord as interval set snapped to the scale.
- On-device faster-than-real-time bounce with FX-tail detection (fits BACKLOG item 4); 303 peaks near 50% of a block.
- 303 extras: direction modes, Euclidean fill, "same as previous"/N-play-M-skip conditions, in-key pad layout, root carried in the scale value, diatonic transposition (BACKLOG 1 and 6).
- Effect idle-skip when input is silent and the tail dead (saves CPU, removes denormal exposure). Low priority: user contour tables for WOBBLE, macro knobs, SD streaming ring (only if a sample unit returns), loadable units.

## Reference read of CE's 3rdparty audio/USB (2026-11-03, maintainer asked "read the repo's data as reference")
Those files are PJRC's Teensy Audio library and Teensy core (MIT, Polyend-modified). Facts only, nothing copied into the repos:
- SAI + codec: CE's I2S setup matches ours (BCLK = MCLK/4, two 32-bit words per frame = 64 Fs, MCLK from the system clock; the only difference is the MCLK fraction, 16/255 for CE vs ours 196/3125). CE writes CHIP_I2S_CTRL 0x0130 (SCLKFREQ 32 Fs) with that 64 Fs BCLK, so the shipping product runs exactly our default; this settles "unknown for CE" in the HW-A E-1 A/B (0x0030 stays an optional experiment, not a fix). CE's codec power-up uses ANA_POWER 0x4060 then 0x40FF, a 400 ms wait, CLK_CTRL 0x0004, SSS_CTRL 0x0010, DAC vol 0x3C3C, HP vol 0x7F7F; same as PJRC upstream, which our sgtl5000.h already cites.
- DAP routing (answers the open question): post-processing the DAC path = DAP_CONTROL 1 + CHIP_SSS_CTRL 0x0070 (I2S -> DAP -> DAC). Pre-processing the mic/line path = DAP_CONTROL 1 + SSS_CTRL 0x0013 (ADC -> DAP -> I2S out, I2S in -> DAC). One DAP only: pre or post, not both. AVC has max gain 0/6/12 dB, integrator 0/25/50/100 ms, threshold, attack/decay, and a "hard limit" mode where the signal saturates at the threshold (a hard clip, not look-ahead). EQ bands at 115, 330, 990, 3000, 9900 Hz. Datasheet still has the last word.
- USB MIDI descriptor: PJRC's MS_HEADER wTotalLength counts header + jacks only (7 + 30 per cable = 37 for one cable) and excludes the endpoints, the same convention as our kit/usb/src/descriptors.cpp. That lowers the descriptor-length doubt (row 2.2 above) but the Windows 11 March-2026 break CE fixed is still unexplained (changelog gives no cause), so the Windows 11 enumeration test stays owed.
- CHANGELOG facts worth knowing: CE streams long samples from SD, keeps the 11.25 MB sample pool on the Original, ~128 KB internal RAM free, ~5.3 MB SDRAM free; its UI has "Play N / Skip M" and "Skip N / Play M" chance conditions (N, M in 1..6) plus group-with-last / not-last; MIDI Continue and Song Position Pointer are now followed.

Second reference read (FT812, LEDs, developer guide, synth SDK and effects docs):
- Bootloader fact from CE's developer guide: the Original's on-chip bootloader reads `/Firmware/_fwinfo` into a 32-byte buffer, so a .ptf name of 32+ characters overwrites the terminator (garbage on the flashing screen); keep names <= 31 chars. Ours already guards it (OS-BUG-FWNAMELEN, `update_name_ok` / `Fault::NameLong` in platform/mk66/update/src/fat_firmware_store.cpp); CE's doc just confirms the track3r-os finding. The official updater also lists only files starting with a device prefix and ending .ptf; not ours to follow.
- FT812: CE does write REG_PWM_HZ 9000 on the full-size unit (250 only in the Mini branch), confirmed by reading it; the 3 us waits around CS look like a defensive habit, no evidence of a failure behind them (keep the 1e5 rd16 stress test as the check, low priority). CE sets REG_TOUCH_RZTHRESH 1200 at bring-up "to eliminate false touches", so touch noise may be real: read REG_TOUCH_* once on the unit.
- LEDs: CE keeps a RAM shadow of the IS31FL3731 function registers 0x00..0x0D (except 0x07) and rewrites any that read back different before every LED frame; the full frame is one burst (18 on/off + 18 blink + 144 PWM bytes). Ours reads back only shutdown every 500 ms. The shadow-compare idea is plain defensive programming; worth a soak diag, low priority.
- Memory facts (Original): FLASH ~871 KB of 1024 used, SRAM ~128 KB of 256, SDRAM 11.25 MB sample pool + 1.5 MB delay + 768 KB shared scratch, ~1.1 MB free. Streaming parameters: 32768-frame pre-cache (~743 ms), 16384-frame ring, 4096-frame chunks, FatFs fast-seek link maps; on the M4F they keep slices fully resident because the main loop spends 20-35 ms per step on FT812 redraws. `.ptfx` plugins run from SDRAM with the system MPU disabled (MPU_CESR = 0). Synth SDK: float 128-frame blocks, held-note stack with Always/Overlap/Legato, note-off retriggers the previous held note, no allocation in render, `__fp16` parameter bounds on ARM; synth engines exist only on the M7 devices. Nothing here changes our code; acid_voice already has the held-note stack with legato/slide.

## Agreements (no action)
Flash config field, clock tree, SDRAM controller, pins (all compared), FT812 bring-up order and panel timing, TCA8418 pad and button key maps (all 80 entries each), LED layout, encoder decoding, DIN pins and baud, PTD6 amp key polarity. Where ours differs it is mostly more defensive (underrun handling, CMDB flow control, resync, bounded waits, crash record + reset where CE hangs). CE has no USB audio on the MK66; USB audio and USB disk exist only in ours. Pads in CE are plain switches (no ADC, no velocity).
